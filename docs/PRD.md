# 모임 이벤트관리 PRD

> 기존 `nextjs-supabase-app`(Next.js App Router + Supabase, 구글 OAuth 인증 및 `public.profiles` 테이블만 존재하는 그린필드 상태)에 새로 추가하는 "모임 이벤트관리" 기능에 대한 PRD.

## 1. 목표 / 배경

정기 소모임(수영, 헬스 등 러닝메이트) 주최자는 매번 공지, 참여자 관리, 카풀 배정, 회비 정산을 카카오톡 대화방 + 수기 계산으로 처리하고 있어 반복적인 운영 부담이 크다. 이 반복 작업을 하나의 웹 서비스로 옮겨 주최자의 운영 부담을 줄이는 것이 목표다.

**용어 정의 보정**: "정기 소모임"은 모임의 성격(반복 가능성)을 가리키는 것이지, 지난 회차 이력을 정리·관리해야 한다는 뜻이 아니다. 실제 관리 단위는 **"이번 모임 한 번"**이며, 공지 / 참석자 확인 / 정산 / 카풀만 잘 되면 충분하다. 1회성 모임도 흔하므로 "정기"라는 정의 때문에 1회성 모임 생성이 번거로워져서는 안 된다. 이에 따라 **모임 생성 UX는 그룹과 첫 회차(이벤트)를 한 번에 만드는 단일 플로우**로 설계한다 (그룹→이벤트 2단계 구조를 사용자가 인지하지 않아도 되게).

## 2. 타겟 사용자

- **주최자**: 정기 소모임을 운영하며 여러 참여자를 반복적으로 관리하는 1인. 그룹을 생성하고 공지/참여자/정산/카풀을 관리하는 주체.
- **참여자**: 주최자가 공유한 초대링크로 그룹에 합류하는 멤버. 공지를 조회하고, 회차별로 RSVP하며, 본인의 정산 분담액을 확인한다.

## 3. 핵심 요구사항 (확정된 제품 결정사항)

- **MVP 기능 우선순위** (이 순서로 구현): ① 공지사항 → ② 참여자관리 → ③ 정산관리 → ④ 카풀매칭
- **모임 생성**: 그룹 생성과 첫 회차(이벤트) 생성을 한 번의 플로우로 처리한다.
- **정산관리**: 더치페이 **금액 계산 + 조회만** 제공한다. 실제 결제/PG 연동은 하지 않는다. 정산 관련 알림도 발송하지 않는다(주최자가 카카오톡으로 개인 통지하므로, 앱은 금액만 정확히 계산하면 된다).
- **카풀매칭**: 주최자가 참여자를 차량에 **수동으로 배정**한다. 자동 매칭 알고리즘은 없으며, 좌석 초과는 경고만 하고 배정 자체를 막지는 않는다.
- **인증/회원가입**: 소셜 로그인만 지원한다(구글 OAuth는 이미 구현되어 있음). 이메일/비밀번호 회원가입은 도입하지 않는다.
- **알림**: 이메일만 지원한다. 인앱 알림, 카카오톡 연동은 하지 않는다.

## 4. 사용자 여정

```

1. 로그인 (구글 OAuth)
   ↓
2. 홈 (내 그룹 목록)
   ↓
   [주최자] "모임 만들기" 클릭
   → 모임 생성 페이지 (그룹 정보 + 첫 회차 정보를 한 번에 입력)
   → 생성 완료 → 그룹 홈(첫 이벤트) 이동

   [참여자] 초대링크로 접속
   → 그룹 합류 페이지 (로그인 필요 시 로그인 후 리디렉션)
   → 합류 완료 → 그룹 홈 이동
   ↓
3. 그룹 홈 (이벤트 목록 / 최신 이벤트)
   ↓
   → 공지사항 페이지 (조회, 주최자는 작성도 가능)
   → 참여자관리 페이지 (RSVP, 주최자는 출석체크/로스터 관리)
   → 정산관리 페이지 (지출 등록, 분담액 조회)
   → 카풀매칭 페이지 (차량 등록, 수동 배정)

```

## 5. 기능 명세 (MVP)

각 기능은 구현 순서(①~④)와 무관하게 아래 표 순서로 정리한다. "관련 페이지"는 8절 정보구조의 페이지와 대응한다.

| ID       | 기능명                        | 설명                                                                                                                                                                                                                                           | 관련 페이지                      |
| -------- | ----------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------- |
| **F000** | 그룹+첫 회차 동시 생성        | 주최자가 그룹 정보(이름 등)와 첫 회차(이벤트) 정보(제목, 일시, 장소)를 한 화면에서 입력해 그룹과 이벤트를 동시에 생성                                                                                                                          | 모임 생성 페이지                 |
| **F001** | 초대링크 합류                 | 그룹별 고유 `invite_code`로 발급되는 초대링크를 통해 참여자가 그룹에 합류(로그인 필요)                                                                                                                                                         | 그룹 합류 페이지                 |
| **F002** | 멤버 로스터 관리              | 주최자가 그룹 멤버 목록을 조회하고, 멤버를 제거(소프트 삭제, `status: removed`)할 수 있음                                                                                                                                                      | 참여자관리 페이지                |
| **F003** | 회차별 RSVP                   | 참여자가 각 회차(이벤트)에 대해 참석/불참 의사를 표시                                                                                                                                                                                          | 참여자관리 페이지                |
| **F004** | 출석 체크                     | 주최자가 회차 당일 실제 참석 여부를 체크. 출석 여부는 정산 대상자 판단 기준으로 사용됨                                                                                                                                                         | 참여자관리 페이지                |
| **F005** | 공지사항 등록/조회            | 주최자가 그룹 전체 또는 특정 회차 대상 공지를 작성. 참여자는 조회만 가능                                                                                                                                                                       | 공지사항 페이지                  |
| **F006** | 공지 이메일 발송              | 새 공지 등록 시 그룹 멤버 전원에게 이메일 발송                                                                                                                                                                                                 | 공지사항 페이지 (등록 시 트리거) |
| **F007** | 지출 항목 등록                | 주최자가 이벤트별 지출 항목(제목, 금액, 결제자)을 등록                                                                                                                                                                                         | 정산관리 페이지                  |
| **F008** | 더치페이 분배 계산            | 지출 항목을 균등분배(N분의 1, 원 단위 나머지까지 정확히 배분해 합계가 항상 원금과 일치) 또는 커스텀 금액으로 분배 계산. 대상자는 기본적으로 출석 확인된 참여자(출석 체크 전이면 RSVP 참석자로 폴백)이며, 주최자가 대상자를 제외/포함 조정 가능 | 정산관리 페이지                  |
| **F009** | 분담액 조회 및 정산 완료 체크 | 참여자별 분담액을 표시하고, 주최자가 각 참여자의 "정산 완료" 여부를 수기로 체크                                                                                                                                                                | 정산관리 페이지                  |
| **F010** | 차량 등록                     | 주최자가 이벤트별 차량(운전자, 출발지/시간, 좌석 수)을 등록                                                                                                                                                                                    | 카풀매칭 페이지                  |
| **F011** | 수동 카풀 배정                | 주최자가 미배정 참여자를 원하는 차량에 수동으로 배정. 좌석 수 초과 시 경고만 표시하고 배정은 허용                                                                                                                                              | 카풀매칭 페이지                  |
| **F012** | 구글 OAuth 로그인             | 기존에 구현된 구글 소셜 로그인으로 인증 (신규 구현 아님, MVP 전제 조건)                                                                                                                                                                        | 로그인 페이지 (기존)             |

## 6. 비범위 (MVP에서 제외)

- 실제 결제 / PG 연동
- 카풀 자동 매칭 알고리즘

### RLS 정책 방향

- 조회: 해당 그룹의 멤버(`group_members.status = active`)만 조회 가능
- 쓰기: 기본적으로 주최자(`role = organizer`)만 가능
- 예외: `event_participants`의 RSVP는 참여자 본인이 자신의 row를 쓸 수 있어야 함
- 스키마 변경 후에는 `mcp__supabase__get_advisors`로 RLS 누락 등 보안 경고를 확인하고, `mcp__supabase__generate_typescript_types`로 `database.types.ts`를 재생성한다.

## 9. 기술 스펙

- **프레임워크**: 기존 Next.js (App Router, `cacheComponents: true`), React 19, TypeScript 그대로 사용
- **DB / 인프라**: Supabase MCP를 통해 원격 프로젝트에 직접 마이그레이션 적용 (`mcp__supabase__apply_migration`), 조회는 `mcp__supabase__execute_sql`. 로컬 Supabase CLI(`supabase/` 디렉터리)는 사용하지 않는 기존 관례를 그대로 따름
- **인증**: 기존 `@supabase/ssr` 쿠키 기반 인증 + 구글 OAuth 그대로 사용, 신규 인증 방식 도입 없음
- **폼 처리**: 기존 컨벤션(`"use client"` + `useState` + Supabase 클라이언트 직접 호출)을 그대로 따름. Server Action은 도입하지 않음
- **UI**: Tailwind CSS + shadcn/ui(new-york 스타일) 기존 컴포넌트 체계 사용
- **이메일 인프라**: Database Webhook + Edge Function + Resend 조합으로 공지 등록 시(F006) 이메일 발송
- **타입 동기화**: 스키마 변경 후 `mcp__supabase__generate_typescript_types`로 `database.types.ts` 재생성, `lib/supabase/client.ts` / `server.ts`의 `Database` 제네릭 최신화 확인

## 11. 정합성 체크

- 기능 명세(5절)의 모든 ID(F000~F012)는 8절 정보구조의 페이지에 각각 매핑되어 있다.
- 8절의 모든 페이지는 4절 사용자 여정에서 도달 경로가 존재한다.
- 비범위(6절)에 명시된 항목은 기능 명세, 데이터 모델, 로드맵 어디에도 포함되지 않았다.
- 데이터 모델(7절)의 모든 테이블은 기능 명세의 최소 1개 이상 기능에서 사용된다.
